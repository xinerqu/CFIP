## 为什么需要它

### 问题一：绝大多数工具根本不校验这个 IP 服不服务你的域名

Cloudflare 在全球有几百个机房，跑着同一张 anycast 网。任何一个 CF 边缘 IP 你都能连上、能完成 TLS 握手、能拿到 HTTP 响应。

**但「能连上」和「承载你的 zone」是两件事。**

每个 Cloudflare 账号的域名（zone）只被分配在部分机房上。你把请求发到一个不承载你 zone 的 IP，Cloudflare 会直接回：

```
HTTP/1.1 403 Forbidden
error code: 1034
```

页面上的原文是：

> The host (你的域名) resolved to an IP address that the owner of the website does not have access to.

这个 403 是在**请求进入你的 Worker 之前**就返回的。后面的 CF 内网转发、Worker 执行、回源外网——**一步都没发生**。

而传统优选工具会怎么做？它把这张错误页的下发速度算成「这个 IP 的速度」，报给你一个漂亮的数字。你拿去用，一个字节都过不去。

**实测数据**：20 个候选 IP 里，7 个真的服务、13 个返回 1034。这 13 个如果不过滤，全都会以「看起来很健康」的姿态混进你的结果列表。

**本程序的做法**：两阶段。

- 阶段一：用你自己的域名做 SNI + Host，发一个探测请求。响应体里出现 `error code: 1034`（或 1033 / 1016 / 1020 这类同族错误）就判定为不服务，直接剔除，**连测速都不做**。
- 阶段二：只有确认服务你域名的 IP，才进入吞吐测试。

### 问题二：它测的不是你真实用起来的速度

先看清楚你的流量到底怎么走的：

```
你的电脑  ──①──▶  Cloudflare 边缘节点  ──②──▶  你的 Worker  ──③──▶  目标网站
          （优选IP）    （就是这里）      （CF内网）              （YouTube / GitHub）
```

- **① 本机 → CF 边缘**：这一段由你选的 IP 决定。延迟、丢包、带宽都看它。**这是唯一你能优化的部分。**
- **② CF 边缘 → Worker**：Cloudflare 内部骨干网，你控制不了，通常很快。
- **③ Worker → 目标网站**：Worker 用自己的出口去 fetch 外网。**这一段是免费版 Worker 的真实瓶颈**，而且完全不在传统测速的样本里。

传统优选工具测的是什么？它拿着 `cdn.jsdelivr.net`、`unpkg.com` 这类**托管在 CF 上的静态大文件**去测。

问题在于：这些是 CF 自家的 CDN 静态资源，走的是 CF 专门的静态分发通道，几乎零距离、有缓存、有独立出口。你测出来的 200Mbps，测的是「CF 边缘到 CF 边缘」的下发能力。

**而你刷 YouTube 走的是 ③ 那段 Worker fetch 出口。那是另一条通道，限流更严，还要排队。**

所以会出现这种情况：工具报 200Mbps，实际看 YouTube 卡。不是工具算错了，是它压根没测你真正走的那一段。

**本程序的做法**：在你自己 Worker 上加一个测速端点（`/__speed`），让测速请求**真的穿过 ③** 再回到你这里。

```
你的电脑  ──①──▶  CF 边缘  ──②──▶  你的 Worker  ──③──▶  Google CDN
        ◀────────────────── 数据原路流回 ◀──────────────────
```

这样测出来的数字包含了 ① + ② + ③ 全链路，才是你实际会感受到的速度。

而且回源目标可以选：**Google 视频 CDN**（`redirector.gvt1.com`，会 302 跳到 `*.googlevideo.com`——这正是 YouTube 视频分片走的同一张网）、Google 静态 CDN，或者三个不同的视频 CDN 节点分别对比。

### 传统工具 vs 本程序

| | 传统优选工具 | CFIP优选 |
|---|---|---|
| 测什么 | TCP 握手 / TLS 握手延迟 + 静态 CDN 下发速度 | 两阶段：域名归属校验 + 多流吞吐 |
| 会不会混进 1034 的死 IP | 会，而且会给出漂亮的速度 | 不会，阶段一就剔除 |
| 带宽口径 | 单流，被 BDP 卡死，系统性低估 | 多流并行聚合，可配 1~16 |
| 结果稳定性 | 单次测量，名次随机颠倒 | 重复测量取中位数，波动大主动提示 |
| 是否覆盖回源段 | 不覆盖 | 可覆盖（走自己的 Worker） |
| IP 从哪来 | 自己找、自己筛 | 内置 9 个 IP 库随机生成（含 5 个地区库） |
| 端口 | 只能 443 | 443 / 2053 / 2083 / 2087 / 2096 / 8443，可任意可指定 |
| 运行环境 | 常要 PowerShell 7 / Python / curl | 单 exe + 两个 DLL，双击就跑 |

## 它到底在测什么

### 阶段一：域名归属校验

```
SNI  = 你的域名
Host = 你的域名
GET  /  HTTP/1.1
```

连到候选 IP，用你的域名握手。然后看响应：

- 状态码正常、响应体里没有 CF 错误码 → **这个 IP 服务你的域名** ✅
- 响应体出现 `error code: 1034` → **不服务，剔除** ❌

顺带从响应头的 `CF-RAY` 尾部把机房代码抓出来（`a5d833fd79-SIN` → `SIN`），后面用来显示 `#SG1` 这种国家标签。

### 阶段二：多流吞吐测试

确认服务之后，才开始拉数据。

- 每个 IP 开 N 条并发连接（N = 流数，1~16）
- 每条连接反复请求同一个大文件，直到达到时长上限或字节上限
- 累计所有连接收到的字节数 ÷ 实际耗时 = 速度

这里有个必须处理的坑：有些源忽略 `Range` 请求头，永远返回全量；有些源用 `Transfer-Encoding: chunked` 且不给 `Content-Length`。程序会识别 chunked 终止块（`0\r\n\r\n`）判断一次响应收完，然后在**同一条 keep-alive 连接**上再要一次，反复累加。

### 阶段三：重复测量

`--repeat N` 会对同一个 IP 测 N 次，取**中位数**。极差过大时在结果里标注「极差 XX Mbps」，提醒你这条不可靠。

### 判定顺序

```
1. 阶段一被 1034 拦了          → 剔除「该IP不服务此域名(CF 1034)」
2. 开了「必须服务此域名」但没确认 → 剔除「未能确认该IP服务此域名」
3. 状态码不在可接受列表里        → 剔除
4. 状态码通过后，真实路径模式先查响应头   → 没有 X-Speed-Bytes 就剔除「Worker 没加 /__speed 端点」
5. 有标记但拿不到足够数据        → 剔除「真实路径只回了 xxxB（上游短读，换一条回源线路）」
6. 真实路径拿到 0 字节            → 剔除「真实路径端点无数据(0B)」
7. 收到的字节 < 64KB            → 剔除「无下载体不测速」（防止把错误页算成速度）
8. 延迟超过上限                  → 剔除「延迟超限」
9. 速度低于下限                  → 剔除「速度过低」
10. 全部通过                     → 保留
```

第 7 条特别重要。传统工具最容易在这里出错：服务器返回 403 或 429 的几 KB 错误页，1 毫秒就读完了，按公式算出来是几十 Mbps 的「假速度」。本程序要求正文至少 64KB 才判定为有效测速。

## 下载与运行

到本仓库右侧的 **Releases** 页面，下载 `cfip_gui.zip`，解压后得到五个文件：

| 文件 | 必需 | 说明 |
|---|---|---|
| `cfip_gui.exe` | ✅ | 主程序，双击运行 |
| `libssl-3-x64.dll` | ✅ | OpenSSL 运行库，缺了报 0xC0000135 |
| `libcrypto-3-x64.dll` | ✅ | OpenSSL 运行库，同上 |
| `worker_速度端点.js` | ⬜ | 可选。要用「测真实路径」才需要，见下一节。**v1.8 起不用自己手贴了，程序能一键注入** |
| `README-worker.md` | ⬜ | 可选。只讲 `worker_速度端点.js` 原理和排错的单独说明，比本节更细 |

**必需的那三个放同一个文件夹，双击 `cfip_gui.exe`。**

> 除了这两个 OpenSSL DLL，没有任何其它依赖：不需要 .NET、不需要 VC 运行库、不需要 PowerShell、不写注册表、不写系统目录。Windows 7 SP1 及以上都能跑。
>
> 输出文件（`good_ips.txt`）和输入的 `ips.txt` 都按 **exe 所在目录**解析 —— 相对路径不会跑到「当前工作目录」去。

### 第一次打开

**就记三件事：域名填自己的、测速方式选真实路径、IP 来源随便挑一个库。**

**一、域名填你自己 Worker 绑定的那个**

程序里域名那一栏默认是空的，必须自己填——就是你在 Cloudflare 上给 Worker 绑的域名，形如 `abc.example.com`。

程序拿它做两件事：

1. 阶段一做 SNI + Host，判断这个 IP 是否真的服务你的 zone（不服务的会被 CF 回 1034，直接剔除）
2. 测真实路径时，把请求打到你自己 Worker 的 `/__speed`

**二、测速方式选「真实路径」**

「测速方式」下拉保持默认的 `真实路径：走 Worker 回源（准）` 就行——它本来默认就是这个。

前提是你已经按下一节给 Worker 加过测速端点。**还没加的先加，这是整个工具最有价值的部分**——v1.8 起点一下按钮就自动注入，不用自己动手粘代码。实在不想加，就先选任意一个 `内置源` 测个大概。

**三、IP 来源除了本地，也能直接选在线列表**

「IP来源」下拉一共 10 项，二选一：

- `本地列表文件` —— 你自己准备的 txt
- 另外 9 项都是**现成的在线列表**：4 个通用库（CM优选列表v4 / AS13335列表v4 / AS209242列表v4 / CF官方列表v4，和 edgetunnel 里的完全一样）+ 5 个地区库（日本 JP / 香港 HK / 台湾 TW / 美国 US / 新加坡 SG）

选库之后填个数量（比如 `20`），点「生成」，IP 就自动填进列表了，不用再去别处找。端口那一栏 `任意` 就行，也可以钉死成某一个。

第三行的「回源线路」四个都行，默认第一个（YouTube 视频CDN 1）最贴近看视频的实际情况；哪个跑出来 502 或短读就换下一个。

最后确认「超时ms」填 `5000`（真实路径的 TTFB 常在 700~4500ms，1000 会把好 IP 判死），点「开始测试」。

跑完点「保存」，结果文件一行一个，直接粘进客户端。

## 给你的 Worker 加测速端点

这一节是「测真实速度」功能的前提。

**如果你只想用内置静态源测速，这一节可以完全跳过。**

> 想看得更细（含排错表、参数表、12 条常见问题），同一个 zip 里还有一份只讲这件事的 [`README-worker.md`](README-worker.md)。

### 一键注入：不用手贴代码（推荐，约 30 秒）

以前的版本要你自己在几万行代码里找位置、腾空行、整块粘贴，粘歪一点就报语法错。v1.8 起不需要了。

**GUI 做法：**

1. 先把你的 `_worker.js` 弄到本地：Cloudflare 后台 → Workers & Pages → 你的 Worker → 编辑代码 → 右上角把代码全选复制，存成一个 `.js` 文件（文件名随意，比如 `_worker.js`）
2. 打开本程序，点第五行右边那个 **「给 Worker 一键加测速端点…」** 按钮
3. 选中刚才那个 `.js` 文件
4. 程序在同一个目录生成 `原名_已注入.js`，弹框告诉你完整路径。**原文件一个字节都没改**
5. 打开这个新文件，**全选复制**
6. Cloudflare 控制台 → 你的 Worker → 编辑代码 → **全选删除** → **粘贴** → 点 **Deploy**
7. 回到本程序点「开始测试」。判定列不再报「Worker 没加 /__speed 端点」就通了

**命令行做法：**

```bat
cfip_gui.exe --inject C:\path\_worker.js
```

输出 `C:\path\_worker_已注入.js`。想换个输出名：

```bat
cfip_gui.exe --inject C:\path\_worker.js --injectout C:\path\worker_new.js
```

成功时打印：

```
注入成功，原文件没有改动。

新文件：
 C:\path\_worker_已注入.js

接下来三步：
1. 打开这个新文件，全选复制；
2. Cloudflare 控制台 → 你的 Worker → 编辑代码 → 全选删除 → 粘贴 → Deploy；
3. 回到本程序点「开始测试」，如果判定列不再报「Worker 没加 /__speed 端点」就通了。
```

**程序只做三件事，没有魔法：**

- 在源码里找 `async fetch(` 后面那个 `{`
- 在它后面插一整段测速端点（首尾都有注释标记）
- 写一个新文件，原文件不动

失败也只有两种情况，都会明确告诉你：

| 提示 | 原因 | 怎么办 |
|---|---|---|
| `这个文件里已经有测速端点了，不用再注入。` | 你选的是已经注入过的文件 | 换原始文件，或者先把原来那段（`测速端点开始` 到 `测速端点结束`）删掉 |
| `这个文件里找不到 async fetch(` | 选错文件了，不是 Worker 主脚本 | 确认你选的是 `_worker.js` 本体，不是 `wrangler.toml` 或分包文件 |

### 它插进去的是什么

`worker_速度端点.js` 就是这一整段。作用是让 Worker 多认一个 URL 路径 `/__speed`。

当工具访问 `https://你的域名/__speed?mb=50` 时，Worker 不走代理逻辑，而是去 Google CDN 拉 50MB 数据，边拉边流式返回给工具。**这段数据是 Worker 自己 `fetch` 外网拿回来的**，所以工具测到的速度包含了「Worker 出网回源」这一段——也就是你刷 YouTube 真正走的那一段。

整段长这样（中间省略）：

```js
// ====================== 测速端点开始 ======================
// 这一段是 CFIP 优选IP测速 自动插入的，位置就在 async fetch(...) { 的下一行。
// 你不用改它，也不用管它；它只响应 /__speed 这一个路径，其它请求原样放行。
{
  const 测速URL = new URL(request.url);
  if (测速URL.pathname.toLowerCase() === '/__speed') {
    ...
    return new Response(...);
  }
}
// ====================== 测速端点结束 ======================
```

插进你的文件后是这样：

```js
export default {
  async fetch(request, env, ctx) {
    // ====================== 测速端点开始 ======================
    {
      const 测速URL = new URL(request.url);
      if (测速URL.pathname.toLowerCase() === '/__speed') { ... }
    }
    // ====================== 测速端点结束 ======================
    let 请求URL文本 = ...     // ← 你原来的代码，一个字都不用改
```

三个要点：

1. **最外面那对 `{` `}` 是故意的**。这是一个裸块（block statement），作用是把 `const 测速URL` 限制在块内，不污染后面几万行代码的作用域，避免撞名。
2. **它是独立的 `if`，不是 `else if` 链的一环**。所以碰不到你原有的判断逻辑，处理完 `/__speed` 直接 `return`，不是 `/__speed` 就自然往下走。
3. **首尾两行注释留着有好处**。以后想删的时候能一眼找到边界。

### 验证端点是否生效

浏览器直接打开：

```
https://你的域名/__speed?mb=1
```

应该开始下载 1MB 数据（浏览器可能直接当文件下载，正常）。

更准确的方式是看响应头：

```bash
curl -s -o NUL -D - -r 0-1023 "https://你的域名/__speed?mb=1"
```

看到这两行就说明成功了：

```
X-Upstream-Mode: gvt1-video-cdn
X-Upstream-Landed: rr1---sn-oj5hn5-5t.gvt1.com
```

`X-Upstream-Mode` 告诉你走的哪条线路（`gvt1-video-cdn` 或 `dl.google.com`），`X-Upstream-Landed` 告诉你实际落到了哪个 CDN 节点。

**如果返回 404 或者 613 字节的 nginx 欢迎页** → 这段 JS 没生效，或者插到了 Worker 作用域外面。重新注入一次。

**如果返回 502 `上游全部失败`** → 端点生效了，但你所在的 CF 机房连不上 Google 视频 CDN。换一条回源线路试试（`?u=dl`）。

**其实这些你都不用自己查**：直接在本程序里跑，判定列会告诉你到底卡在哪一步（见下「程序怎么判断端点没加」）。

### 程序怎么判断端点没加

真实路径模式下，工具会检查响应头里有没有 `X-Speed-Bytes` 或 `X-Upstream-Mode`：

| 判定列显示 | 含义 | 怎么办 |
|---|---|---|
| `Worker 没加 /__speed 端点(613B页面)→ 先粘贴测速片段` | 拿到的是 nginx 欢迎页，端点不存在 | 用一键注入重新生成文件并部署 |
| `真实路径只回了 xxxxxB（上游短读，换一条回源线路）` | 端点生效了，但上游只给了一点数据就断 | 换回源线路（GUI 第三行下拉，或 URL 加 `&u=dl` / `&n=1`） |
| `真实路径端点无数据(0B)：Worker 的 /__speed 没生效` | 端点通了但一个字节都没回来 | 同上，先换线路；一直 0B 就是机房出网有问题 |

为什么不用 `Content-Length` 判断？因为 Cloudflare 在 `TransformStream` 之后会强制把响应改成 `Transfer-Encoding: chunked`，那个头会被丢掉。

### 参数说明

端点支持四个 URL 参数：

| 参数 | 取值 | 说明 |
|---|---|---|
| `mb=N` | 1~200，默认 50 | 返回多少 MB 数据 |
| `u=dl` | 任意值 | 换成 Google 静态 CDN（`dl.google.com`），不写就走视频 CDN |
| `n=N` | 0 / 1 / 2 | 从视频 CDN 的第几个源开始（程序会轮转），用来换线路重试 |
| `token=` | 字符串 | 只有你在 Worker 里设了 `SPEED_TOKEN` 环境变量时才需要 |

`n` 参数的效果是轮转。比如 `n=1` 时，候选顺序变成 [源2, 源3, 源1]，第一个挂了自动试下一个。

### 为什么这么设计（技术细节）

**1. 为什么用 `globalThis.fetch` 而不是 `fetch`？**

在 Worker 的模块作用域里，裸 `fetch` 有可能被解析成你自己定义的东西，最坏情况是递归调用到自己的 handler。加 `globalThis.` 明确指向平台提供的那个 fetch，多一层保险。

**2. 为什么要在客户端手动截断？**

`redirector.gvt1.com` 会 302 跳到 `*.googlevideo.com`。跳转过程中 `Range` 请求头**可能丢失**，上游会一股脑返回完整的 781MB。

所以代码里挂了一个 `TransformStream`，发到 `字节数` 就硬切：

```js
const 截断 = new TransformStream({
  transform(chunk, ctrl) {
    if (已发 >= 字节数) return;
    const 剩 = 字节数 - 已发;
    if (chunk.byteLength > 剩) {
      已发 = 字节数;
      ctrl.enqueue(chunk.slice(0, 剩));
    } else {
      已发 += chunk.byteLength;
      ctrl.enqueue(chunk);
    }
  },
});
```

没有这段，你请求 50MB 可能会被灌 781MB，直接打爆 Worker 的内存和你的流量。

**3. 为什么响应是 chunked 而不是带 Content-Length？**

代码里虽然写了 `Content-Length` 头，但 **Cloudflare 在 `TransformStream` 之后会强制改成 `Transfer-Encoding: chunked`**，那个头会被丢掉。工具端已经能正确累加 chunked 长度，不影响测速结果。

**4. 为什么上游要按顺序试三个源？**

三个 gvt1 源在不同机房的可达性不一样。实测本机直连时 `emulator` 那个源三次全是 302 循环取不到数据，但 CF 出口调度不同，在 Worker 里反而是可用的。

所以代码里是 `for (const 地址 of 候选)` 依次 try，第一个 `ok` 或 `206` 就采用，全挂了才返回 502。

**5. 为什么默认走视频 CDN 而不是 `dl.google.com`？**

因为 YouTube 的视频分片走的是 `*.googlevideo.com`，和 `redirector.gvt1.com` 是同一张网。测这张网，比测 `dl.google.com`（普通静态下载 CDN）更贴近你看视频的实际情况。

想对比的话，加 `&u=dl` 就行。

### 额度消耗

一次测速请求 = 一次 Worker 请求。

Cloudflare 免费版每天 10 万次请求额度。跑 20 个 IP、每个重复 3 次 = 60 次请求，占 0.06%。

可以忽略不计。

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 部署后报 `Unexpected token 'else'` | 用了旧版手贴方法，粘成了 `} else if (...) {` 形式 | 用 v1.8 的一键注入重来，它插的是独立裸块 |
| 部署后报 `Unexpected token '{'` | 手贴时少复制了首尾某一个括号 | 同上 |

## 功能与特色

### 1. 两阶段校验：先确认归属，再测速度

这是本程序存在的第一个理由。

阶段一用你的域名做 SNI + Host 探测，检查响应体里有没有 CF 的 `error code: 1034`。只有确认服务你域名的 IP 才进入阶段二。

**实测**：20 个候选 IP，7 个服务、13 个是 1034。这 13 个不是「慢」，是**完全不可用**——但传统工具会全给它们打上健康标记。

界面上被剔除的会显示「该IP不服务此域名(CF 1034)」，一眼就能看出来。

你也可以在 GUI 里取消勾选「必须服务此域名」，或者在 CLI 加 `--norequirezone` 关掉这个检查——但除非你在做诊断，没理由关掉它。

### 2. 多流并行：解开 BDP 的死结

单条 TCP 连接能跑多快，受**带宽时延积**（Bandwidth-Delay Product）限制：

```
吞吐上限 ≈ 接收窗口大小 ÷ 往返时延
```

跨太平洋 RTT 150ms 的时候，单条连接不管你带宽多大，都会被这个公式锁死。

**实测同一个 IP、同一个源**：

| 并发连接数 | 实测速度 |
|---|---|
| 1 | 142.6 Mbps |
| 2 | 320.3 Mbps |
| 4 | 285.5 Mbps |
| 6 | 281.7 Mbps |
| 8 | 355.9 Mbps |

单流会**系统性低估**，而且低估的程度随 RTT 变化——这意味着它不只是数字偏小，还会导致**名次颠倒**：本来 4 条流能跑满的 IP，单流测出来可能被另一个低 RTT 但低带宽的 IP 反超。

本程序支持每个 IP 开 1~16 条并发连接（`--streams`，默认 4）。

### 3. 重复测量取中位数：对付噪声

相邻 IP 的速度常只差 3%~8%，而单次测量的波动有多大？

**实测 7 个 IP、32MB 源、连跑 5 次**：变异系数（CV）只有 1.7%~2.6%，看起来很小。但名次呢？

用 `--repeat 1` 分三次跑，三次的名次**互相颠倒**。

所以程序支持 `--repeat N`，测 N 次取中位数。极差超过阈值时，结果里会标注「极差 XX Mbps」，提醒你这条不可靠。

要严格排前几名，`--repeat 3 --threads 1` 是标配。

### 4. 区分「IP 级并发」和「流级并发」

这两个经常被搞混，但作用完全相反：

| 参数 | 含义 | 什么时候调 |
|---|---|---|
| `--threads` | 同时测**几个 IP** | **测排序时必须设 1** |
| `--streams` | 每个 IP 开**几条连接** | 保持 4 左右，模拟实际拉流并发度 |

为什么 `--threads` 必须设 1？因为多个 IP 同时测会**互相抢本机带宽**。实测 `--threads 2` 时全部 IP 的速度从 140~225Mbps 掉到 102~157Mbps——全都变慢了，而且慢的比例各不相同，名次直接乱掉。

本机的带宽是被测对象共享的，同时测就是互相干扰。

### 5. 能测「真实回源路径」

这是本程序存在的第二个理由，也是它和所有传统工具最本质的区别。

配合 `worker_速度端点.js`，测速请求会真的穿过「CF 边缘 → 你的 Worker → 外网」，包含回源那一段。

回源线路可选：

| 线路 | 上游 | 大小 | 适用 |
|---|---|---|---|
| 视频CDN 1 | ndk-r27 (gvt1) | 781MB | 默认，最贴近 YouTube 分片 |
| 视频CDN 2 | emulator (gvt1) | 412MB | 线路 1 挂了时用 |
| 视频CDN 3 | build-tools (gvt1) | 58MB | 小文件，快 |
| Google 静态CDN | dl.google.com | 152MB | 更稳，不会短读 |

**重要预期管理**：真实路径模式的数字会比静态源低**两个数量级**。

静态源能测出 200Mbps，真实路径可能只有 0.4~1.3Mbps。

这不是程序坏了。这是 **CF 免费版 Worker 的 fetch 出网通道的真实上限**。换上游域名也没用——实测 `gvt1` 和 `dl.google.com` 都在 0.5~1.7Mbps 区间，瓶颈不在上游选哪个域名，在 Worker 的出口本身。

**这才是你刷 YouTube 时真正能拿到的上限。** 传统工具给不了你这个数字，因为它压根不测这一段。

### 6. 内置 9 个 IP 库，不用自己找 IP

不用再去 TG 群里求 IP 列表了。

**通用库（从 CIDR 段里随机生成地址）**

| 库 | 数据源 | 内容 |
|---|---|---|
| CM优选列表v4 | cmliu 维护的 CF-CIDR | 精选 CF 段 |
| AS13335列表v4 | ipverse AS13335 | Cloudflare 全部 IPv4 段 |
| AS209242列表v4 | ipverse AS209242 | Cloudflare 另一组 ASN 段 |
| CF官方列表v4 | 实时 CF 官方端点 | CF 当前公布的段 |

**地区库（BestCF 整理好的现成 IP，直接抽行）**

| 库 | 数据源 | 规模 |
|---|---|---|
| 日本 JP（地区库） | `bestcf.pages.dev/random-region/JP/all.txt` | 约 320 条 |

| 新加坡 SG（地区库） | `bestcf.pages.dev/random-region/SG/all.txt` | 约 410 条 |

前四个是从 CIDR 里随机抽 IP，抽的时候会跳过网络地址和广播地址（这点比 edgetunnel 原版更严谨）。后五个是从 BestCF 已经整理好的地区列表里直接抽行 —— 那些行本身就带着 `ip:port`，所以「端口」下拉选「任意」时会沿用列表自带的端口，只有你显式指定了某个端口才覆盖。

地区库的好处：这些 IP 是别人已经筛过一轮、确认落在对应地区的，比自己从 AS13335 全段里瞎抽命中率高得多。想要 JP/HK/TW 的低延迟，直接从对应地区库里抽最省事。

### 7. 端口可选，而且是真随机

edgetunnel 原版的随机 IP 生成逻辑是：

```js
const cfport = [443, 2053, 2083, 2087, 2096, 8443];
const 目标端口 = 指定端口 === -1 ? cfport[Math.floor(Math.random() * cfport.length)] : 指定端口;
```

**IP 和端口纯随机配，零验证。**

为什么不需要验证？因为这 6 个是 Cloudflare 官方文档里的「代理可用 HTTPS 端口」（另有 HTTP 的 80/8080/8880/2052/2082/2086/2095）。同一台 CF 边缘同时监听全部这些端口，所以任意 IP 配任意一个都成立。

本程序的下拉框：

- `任意` = 每个 IP 随机配一个（等价 edgetunnel 默认行为）
- `443` / `2053` / `2083` / `2087` / `2096` / `8443` = 全部用这一个

> 注意：部分 IP 在非标端口上会连不上（TLS 握手超时），这是那个 IP 自身的出网策略，不是配置错误。换一个端口或换一个 IP 即可。

### 8. 结果带机房和国家，一行一个直接可用

输出：

```
104.18.45.150:443#SG1 412ms 87.34Mbps
172.67.69.26:443#DE1 388ms 62.11Mbps
104.17.126.91:443#US1 521ms 45.02Mbps
```

`#SG1` 怎么来的：

1. 阶段一的响应头里抓 `CF-RAY: a5d833fd79-SIN`
2. 取尾部 3 位得机房代码 `SIN`
3. 内置 **311 条 IATA → 国家代码** 映射表转成 `SG`
4. 同国家的按出现顺序编号：`SG1` `SG2` `SG3`

为什么不直接用 `trace.colo`？因为实测发现部分 IP（如 `8.39.125.40`）对 `cloudflare.com/cdn-cgi/trace` 返回的 trace 里 `colo` 是空的，而 `CF-RAY` 头始终可靠——**连 1034 的 403 响应都带 `CF-RAY`**。所以从头里拿，零额外请求，且更稳。

**同机房内 IP 差异只有 3%~8%，跨机房差异可能是几倍。** 所以按国家/机房分组看，比混着排更有意义。

### 9. 延迟口径可选

三个口径，对应三种不同的体感：

| 口径 | 测的是什么 | 典型值 |
|---|---|---|
| TCP 连接 | 只到 TCP 三次握手完成 | ~110ms |
| TLS 握手完成 | 到 TLS 握手结束（和你 clash 里看到的延迟最接近） | ~780ms |
| 首字节 TTFB | 到 HTTP 响应的第一个字节 | ~730ms |

默认选 TLS 握手。

### 10. 超时是两层的

`--timeout` 是**单个 IP 的上限**，不是每个 IP 都等这么久。首字节一到就不等了，只有卡住的 IP 才吃满。

TCP 连接另有一层更短的超时：`min(2000ms, --timeout)`。

**效果**：死 IP 在握手阶段 2 秒内就被淘汰，不会拖累后面一堆慢 IP。只有真的能连上但响应慢的 IP，才会用满你设的长超时。

### 11. 过滤与排序

- **延迟上限**（`--maxdelay`）：超过就丢弃
- **速度下限**（`--minspeed`）：低于就丢弃
- **可接受状态码**（`--codes`）：默认 `200,301,302,400,403,404`
- **排序**：`按速度降序` / `按延迟升序`，二选一，没有「不排序」（避免你拿到一堆乱序结果）

### 12. 输出模板可自定义

支持的占位符：

| 占位符 | 含义 |

| `{port}` | 端口 |
| `{cc}` | 国家代码（SG / HK / US / JP） |

### 14. 代理检测：先确认你测的是不是真的

这是 v1.7 新加的，也是最实用的一条。

**问题**：你开着 clash / mihomo / v2rayN 的时候 —— 不管它跑在你自己的电脑上，还是跑在路由器上 —— 你程序里连出去的流量可能根本没出你家宽带，而是先送进了代理节点。这时候**你测的不是「目标 IP ↔ 你」的速度，而是「目标 IP ↔ 代理节点 ↔ 你」的速度**。后者跟你实际翻墙体验毫无关系，还常常比真实值高好几倍，因为它测的是机房之间的链路。

**只检测、不绕过。** 早期版本试过用 `IP_UNICAST_IF` 把 socket 钉在物理网卡出口上绕开本机 TUN，实测确实有效（绑上网卡后连黑洞地址能正确超时、连真实 CF IP 依然 143ms）。但**如果代理跑在路由器上，网卡绑定就完全没用了** —— 因为拦截发生在你的电脑之外。既然本机开关 clash 只是点一下的事，就没必要为它做一套绕过机制，反而容易让人以为「勾了就能开代理测」。所以现在只做检测 + 提示，让你自己关掉。

程序判两件事，任意一件成立就报「检测到代理」：

**信号 A —— 本机级（TUN / 系统级透明代理）**

连一个**保证不存在服务**的地址（RFC 5737 保留段 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`，600ms 超时）：

- 真直连：必然超时（数据包发出去没人应答）
- 被 TUN 接管：**几毫秒就「连上」了**（TUN 在本机直接代答 SYN，包根本没出网卡）

**信号 B —— 网关级（路由器上的代理、或按域名分流的规则）**

这是关键的一条，因为**路由器级代理抓不到信号 A** —— 你家电脑的网络栈是干净的，黑洞地址照样干净超时，但真正的流量在路由器那一跳被转走了。

做法是**对比两个出口 IP**：

1. 用国内纯 HTTP:80 的回显服务问「我现在的公网 IP 是多少」（`ip.3322.net`、`ddns.oray.com/checkip`、`myip.ipip.net` 依次试）。这类请求不会被代理的域名分流规则命中，拿到的就是你家宽的真实出口。
2. 用**测速时实际会走的那条路径**再问一次：`<待测 CF 边缘 IP>:443` + 测速实际会用的那个 SNI，去请求 `/cdn-cgi/trace`，从响应正文里读 `ip=`。
3. 两个 IP 不一致 → 这条测速路径被转到了代理节点上，数据不可信。

实测（本机，路由器上开着 clash）：
```
家宽真实出口（HTTP:80 回显）      = IP1
测速路径出口（CF trace，443）     = IP2   colo=SJC
```
一个是国内家宽，一个是某个海外机房 —— 一眼就能看出测速流量被转走了。同一时刻直接 curl `https://your.domain.com/cdn-cgi/trace` 出口又是 IP1，说明路由器上是**按域名分流**的（自己的域名走直连，`unpkg.com` / `cdn.jsdelivr.net` / `cloudflare.com` 走代理）。

**结果怎么显示**

第六行右侧那行灰字，启动时自动跑一次，点「开始测试」前再跑一次。四种文案：

| 文案 | 含义 |
|---|---|
| `直连（出口 1.2.3.4）→ 数据可信` | 两个信号都没触发，测的是真实值 |
| `代理：黑洞地址秒连 8ms → 请关代理再测` | 本机有 TUN |
| `代理：家宽 1.2.3.4 ≠ 测速 5.6.7.8 → 请关代理再测` | 网关级代理（路由器） |
| `代理：家宽 1.2.3.4 ≠ 测速 5.6.7.8（黑洞秒连 8ms）→ 请关代理再测` | 两层都有 |

检测到代理时，点「开始测试」会弹框拦一下（可以选「是」强行继续，但数据没意义）。

**命令行对应**：结果打在 stderr 第一行 `[代理自检] …`。加 `--trace` 能看到探测细节：
```
[trace] egress probe 104.18.39.119:443 sni=unpkg.com -> status=200 body=[fl=... ip=IP2 ...]
[trace] 黑洞秒连=1(8ms) 家宽出口=IP1 测速路径出口=IP2 -> state=4
```

**注意**：
- 如果代理是「系统代理」模式（Windows 设置里那个 HTTP 代理），本来就影响不到本程序 —— 它用原始 socket，不读 Windows 的代理设置。
- 如果代理按域名分流，把内置测速源（`unpkg.com` 等）放进了直连列表，那信号 B 也会是「直连」，此时测静态源是准的；但「真实路径」模式走的是你自己的域名，照样能查。
- 出口回显服务全部不可达时会显示「出口探测失败」，此时只靠信号 A 判断，可能漏掉网关级代理。

| 测速方式 | 6 个选项。默认 `真实路径：走 Worker 回源（准）`。前 5 个是内置源，最后一个是真实路径。二者互斥 |

| 控件 | 说明 |
|---|---|
| IP来源 | 下拉。`本地列表文件` 或 9 个 IP 库之一（4 个通用库 + 5 个地区库）。**选库时文件框自动禁用，反向亦然** |

## 用法建议

### 测静态源（快速摸底）

```bat
cfip_gui.exe --cli --domain abc.example.com --iplib 1 --ipcount 50 ^
  --threads 1 --streams 4 --repeat 3 --timelimit 5 --sort speed
```

这个组合会在几十秒内跑完 50 个 IP，给你一个初步排序。适合快速筛掉大部分差 IP。

### 测真实路径（决定最终用哪个）

```bat
cfip_gui.exe --cli --domain abc.example.com --ipfile candidates.txt ^
  --realpath --threads 1 --streams 2 --repeat 5 --timelimit 20 --timeout 5000
```

先用静态源筛出 10 个左右，再把它们放进 `candidates.txt` 跑这一轮。这个才决定你实际用哪个。

### 几个必须记住的点

**测排序时 `--threads 1`。** 多个 IP 同时测会互相抢带宽，快慢全乱。

**`--repeat 3` 不能省。** 相邻 IP 差距本来就小（3%~8%），单次测量基本靠运气。

**真实路径超时给 5000。** 走 Worker 回源 TTFB 常在 700~4500ms，1000ms 会把好 IP 判死。

**真实路径的绝对值不要和静态源比。** 差两个数量级是正常的，它们测的根本不是同一段。

**同机房内不要过度纠结。** 同一个国家/机房的 IP 差异只有 3%~8%，这个量级下 `--repeat 5` 也未必能稳定分辨。不如换机房比较。

## 常见问题

**Q：双击报 0xC0000135 / 提示缺 DLL？**

缺 OpenSSL 运行库。把 `libssl-3-x64.dll` 和 `libcrypto-3-x64.dll` 放到 exe 同一个文件夹。

**Q：全部 IP 都显示「该IP不服务此域名(CF 1034)」？**

两种可能：域名填错了，或者这批 IP 确实都不服务你的 zone。先核对域名是不是你自己的、拼写对不对。如果域名没错而全部 1034，说明这批 IP 的机房不在你 zone 的分配范围里，换一个 IP 库重试。

**Q：判定列显示「Worker 没加 /__speed 端点(613B页面)→ 先粘贴测速片段」？**

程序已经从响应头上认出来了：这个路径回的是普通网页，不是我们的测速端点。

**这一条是新增的判定**，专门把「端点没加」和「端点加了但上游短读」区分开——两者症状完全不同，以前都混在「无下载体」里，看不出来是该去改 Worker 还是该换回源线路。

判据很硬：Worker 端点一定会带这两个响应头

| 头 | 含义 |
|---|---|
| `X-Speed-Bytes` | 这次要返回多少字节 |
| `X-Upstream-Mode` | 走的是视频 CDN 还是 Google 静态 CDN |

缺这两个头就不可能是我们的端点。为什么不用 `Content-Length` 判断——因为 CF 在 `TransformStream` 之后会强制改成 `chunked`，`Content-Length` 被丢掉了。

排查顺序：

1. `worker_速度端点.js` 没粘，或者粘了没 Deploy。按上面第五步用 curl 验证，看有没有 `X-Upstream-Mode` / `X-Speed-Bytes`。
2. curl 有这两个头、工具却报这一条 → 「测速路径」框里手填了别的路径（比如上次测试残留的 `/__nope`）。清空路径框即可，程序会自动补 `/__speed?mb=50`。
3. 用的是 Pages 而不是 Workers 时，`_worker.js` 要放在 Pages 项目根目录，改完要重新部署。

对应的 grep 关键词：判定列搜「没加 /__speed 端点」。

**Q：真实路径模式全部「上游短读」？**

上游给了数据但没给够就断了。换一条回源线路（第三行下拉）。实测 gvt1 在部分机房会短读，Google 静态 CDN（`--upstream 3`）更稳。

**Q：真实路径只有 0.x Mbps，是不是程序坏了？**

不是。这是 Worker 免费版 fetch 出网通道的真实上限。换上游域名也没用，实测都在 0.5~1.7Mbps 区间。这个数字虽然难看，但它才是你刷 YouTube 时的真实天花板。

**Q：开着梯子能不能测出真实值？**

看梯子的形态：

| 形态 | 能测出裸连值吗 | 原因 |
|---|---|---|
| 纯直连 | ✅ 能 | 没有拦截 |
| 只有系统代理 | ✅ 能 | 本程序用原始 socket，不读系统代理设置 |
| TUN 模式虚拟网卡 | ❌ 不能 | TUN 接管全部流量，测到的就是经过代理之后的值 |

判断方法：

```powershell
# 看有没有 TUN 网卡
Get-NetAdapter | Where-Object Status -eq 'Up'

# 看默认路由走哪
Get-NetRoute -DestinationPrefix "0.0.0.0/0"
```

如果有 `clash` / `mihomo` / `wintun` 之类的虚拟网卡在 Up 状态并且持有默认路由，那就是 TUN 模式。

**Q：为什么结果里有些 IP 没有国家代码，显示 `XX`？**

那个 IP 的响应头里没有可解析的 `CF-RAY`（极少数情况，或者用了非 CF 的 IP）。程序会用 `XX` 占位。

**Q：能不能只输出 IP 不输出速度？**

改输出模板为 `{ip}:{port}#{cc}{n}`，就只输出 `1.2.3.4:443#SG1`。

**Q：结果文件编码是什么？**

UTF-8，没有 BOM。Windows 记事本打开可能显示乱码，用 VS Code / Notepad++ 或者设置记事本编码为 UTF-8。

### v1.7

**这一版加了两件事：开始测速前先告诉你「你现在测的到底是不是真的」，以及把「Worker 端点没加」和「上游短读」这两种完全不同的失败区分开。**

- **新增「Worker 端点存在性」判定**：真实路径模式下先从响应头找 `X-Speed-Bytes` / `X-Upstream-Mode`，两个都没有就说明请求根本没走到你粘贴的测速片段（典型症状是回了 613B 的 nginx 欢迎页）。以前这种情况被笼统报成「无下载体」，看不出是「该去改 Worker」还是「该换回源线路」
- **新增「代理检测」**（只检测、不绕过）
  - **信号 A（本机级）**：用 RFC 5737 保留地址（`192.0.2.1` / `198.51.100.1` / `203.0.113.1`）探本机是不是被 TUN 之类的透明代理接管了 —— 这些地址保证没有任何服务在监听，真直连必然超时，而 TUN 会在几毫秒内把 SYN 代答掉。
  - **信号 B（网关级）**：对比两个出口 IP。一边用国内纯 HTTP:80 回显服务拿「你家宽的真实出口」；另一边用 `<待测 CF 边缘 IP>:443` + 测速实际会用的 SNI 去请求 `/cdn-cgi/trace`，读正文 `ip=`，拿「这条测速路径的出口」。两者不一致 = 流量在路由器那一跳被转进了代理节点。
  - 结果四种状态显示在界面第六行右侧：`直连（出口 IP1）→ 数据可信` / `代理：黑洞地址秒连 Nms → 请关代理再测` / `代理：家宽 IP1 ≠ 测速 IP2 → 请关代理再测` / `代理：家宽 IP1 ≠ 测速 IP2（黑洞秒连 Nms）→ 请关代理再测`。检测到代理时点「开始测试」会弹框拦一下（可以强行继续，但数据没意义）。
  - 命令行结果打在 stderr 第一行 `[代理自检] …`；加 `--trace` 能看到探测细节与两个出口 IP。
- **为什么重要**：开着代理时，程序连任何 IP 都可能在别处被转发。这时测出来的延迟和速度是「那个 IP ↔ 代理节点 ↔ 你」的综合值，跟你要找的优选 IP 无关 —— 甚至会把已经黑洞的 IP 测成 100Mbps 的「优质 IP」。这一版就是用来挡住这种假数据的。
- **为什么是检测而不是绕过**：早期做过一版用 `IP_UNICAST_IF` 把 socket 钉在物理网卡出口上来绕开本机 TUN，本机 TUN 场景确实有效。但**代理跑在路由器上时网卡绑定毫无作用**（拦截发生在电脑之外），而本机开关代理又只是点一下的事。所以最终只保留检测 + 提示，把「绕不绕过」的决定权交回给你。
- 版本号 1.6 → 1.7
- `--version` / `--checkupdate` 现在能区分「有新版本」「已是最新」「本地版本比发布版还新（开发版）」三种情况，退出码有新版时返回 1
